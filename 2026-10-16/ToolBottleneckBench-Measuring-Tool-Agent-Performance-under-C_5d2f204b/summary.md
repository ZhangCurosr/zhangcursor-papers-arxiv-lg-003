# 论文速读：ToolBottleneckBench-Measuring-Tool-Agent-Performance-under-C

## 一句话总结
本文提出 ToolBottleneckBench，通过在固定任务与冻结 Harness 预算下单独施加四种压力（目录、菜单、工作流、编码），实现 Tool Agent 模型能力与系统限制的可控解耦评估；核心发现是可见菜单的性能惩罚主要由 completion cap 截断驱动，且仅靠更换模型配置不如引入路由器或委托控制器等修复策略有效。

## 研究问题与动机
- 现有 Tool Agent 评测通常只报告单一成功率，无法区分失败源于模型自身能力不足还是 Harness 限制（工具菜单大小、上下文截断、调用/轮次预算等）。
- 真实环境中多个负载常同时变化，现有受控基准虽固定目标，但未记录导致失败的具体 Harness 限制，使故障归因缺乏因果依据。
- “首次未满足义务”标签（如“工具选择失败”）易产生误导：大量被标为 selection 的失败实际发生在模型做出任何调用之前，原因是首响被截断。
- 缺乏系统性的修复验证协议，难以判断“针对压力的修复”与“切换底层模型配置”哪个更具工程性价比。

## 核心贡献（创新点）
- **提出 ToolBottleneckBench 受控基准**：通过确定性编译器在同一任务族上每次只改变一个压力（R/V/W/D）生成配对变体，实现严格的因子对照实验设计。
- **定义 Failure Record 机制**：精确评分器按序检查 9 项义务，记录首个未满足项与触发终止的 Harness 限制，将故障标签与终止原因结构化绑定。
- **构建修复对比协议与量化指标**：提出 L/Γ/Σ/Δ 激活量框架，系统测试路由、菜单裁剪、提示词、编码接口及公共交接控制器，并与每 21 种配置切换进行成功率/成本 Pareto 比较。
- **开源完整评估生态**：发布确定性任务生成器、精确评分器、全部带分数据行及分析代码，支持跨研究复现与后续扩展。

## 方法详解
- **任务族与匹配变体**：设计 36 个任务族（嵌套于 12 个企业意图：会计、邮件、文件、日历），固定用户请求、事实值、决策标签、证据引用规则、允许状态转移及工具身份；确定性编译器仅改变单一压力产出配对变体，配对差值即该压力的因果效应。
- **四种 Assigned Pressure**：
  - **R（注册目录）**：工具注册集合大小（32/512/2048），冻结检索器返回 16 个候选；分离评估可用性 A 与选择 S，ITT 成功 = A·S。
  - **V（可见菜单）**：模型实际看到的 Schema 数量（8/32/128），操作工具始终可见，新增项为 workspace/region/collection 不同的干扰邻居；Schema 字节从 3,481 增至 55,176。
  - **W（认证工作流）**：要求的最少有效调用数与依赖深度（低/中/高，对应 2/4/6 次读取 + 1 次可逆动作调用）；配套 Frontier 扩展至 0/2/6/14/30 次公开交接调用。
  - **D（返回状态编码）**：原始 JSON / compact 字典元组 / typed 类型对象 / linked 链接对象，解码值完全等价但格式开销不同。
- **冻结 Harness 契约**：统一 completion cap = 1,024 tokens/request；episode budget = 128,000 tokens；call limit = 认证最小值+2；turn limit = call limit+2；成功不可行时触发 early stop；默认采用 routed menu（首次执行操作工具后菜单缩窄至仅操作工具），并保留 fixed-menu 配对车道。
- **精确评分与失败记录**：按序验证 Y = A ∧ S ∧ P ∧ Q ∧ E ∧ X ∧ G ∧ B ∧ C；任一未满足即记录为首个未满足义务，并结合终端标志（截断/超预算/转数限制/不可行/错误结论/其他违约）构成 Failure Record。
- **统计与修复评估**：主分析以 36 个任务族为聚类单位，10,000 次百分位 Bootstrap 生成 95% CI，配合 Holm 多重校正；修复激活通过交集-并集检验判定，并与配置切换进行配对 Pareto 比较。

## 实验与结果
- **数据规模**：21 个配置（来自 Anthropic、OpenAI、Google、Alibaba、DeepSeek、Tencent、Z.ai 等 7 家机构），共 26,576 个评分条件，其中 20,408 条使用精确 VTS 评分。
- **压力主效应**：整体平均 VTS 为 82.1%。仅有 V 产生显著惩罚：从 8 增至 128 使 VTS 下降 −12.3 pp [−14.6, −9.9]（Holm p<.001），全菜单可见时为 −17.5 pp；W 整体效应 +0.8 pp [−1.2, 2.8] 不显著，各配置间存在正负抵消；D 中 compact 编码 −3.7 pp，typed/linked 无显著效应。
- **截断驱动机制**：V=128 时的菜单惩罚与 completion cap 截断率高度相关（Pearson r = −0.95）。在 6 个高截断配置中，将 cap 提高 16 倍至 16,384 后，菜单惩罚从 −43.7 pp 降至 −2.7 pp，交互效应 41.0 pp [36.2, 45.5]，证明大部分惩罚源于截断而非模型能力。
- **故障分布特征**：3,725 次失败中 91.5% 结束于 Harness 限制（28.7% 截断、50.0% 超预算/调用限制、12.8% 可行性早停），仅 5.5% 为错误结论；所有 849 个标记为“selection”的失败样本实际均未发起任何调用。
- **失败记录诊断力**：基于 Failure Record 预测所分配压力的解码器平衡准确率为 48.9%~54.1%，低于仅凭工具调用次数分箱的 54.8%。
- **修复有效性**：仅 3 种修复激活：连接器优先路由器（ITT 提升 58.1 pp）、路由菜单（Γ=4.9 pp）、公共交接控制器（结构留外集 Γ=96.6 pp）。提示词修复均未激活。路由器与控制器在所有配置切换中均取得成功率优势，控制器将 30 调用 Frontier 的超预算失败从 3
